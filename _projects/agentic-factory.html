A three-part investigation into what it actually takes for AI agents to run a factory: a benchmark comparing coding-agent frameworks against each other under identical conditions, an academic comparison of agent-coordinated production against the traditional discrete-event simulation (DES) approach, and a natural-language demonstrator where describing a production design out loud gets it built and run live on the factory floor.

Why this, and why now

Every vendor claims their agent framework is the one that gets real work done unsupervised; almost none of that is backed by a fair, repeatable comparison run under identical conditions. Agentic Factory starts from that gap and works outward in three directions at once: can these frameworks be benchmarked fairly against each other at all (HarnessBench), does agent-based coordination actually beat the traditional operations-research approach to modelling a factory (the DES comparison), and, if it does work, can that be shown rather than just claimed (the natural-language demonstrator).

Background: is a simple controller enough?

Before building any of the three parts above, it was worth asking a more basic question first: for a bounded operations problem, how much does an autonomous LLM agent actually buy you over a plain rule-based controller? Vending-Bench (Backlund & Petersson, 2025) is a published benchmark for exactly this: it scores autonomous LLM agents managing a simulated vending machine, inventory, restocking, pricing, cash, supplier emails, over a long horizon, and reports results for nine LLMs plus a human baseline, ranked on final net worth.

Rather than take that at face value, a discrete-event simulation (DES) of the same environment was built, driven by a fixed, deterministic controller reading only a restricted observation of the environment, the same information an LLM agent would have, not privileged access to the simulation's internal state. Across 50 seeds, that simple controller reached a mean net worth of $3,643.90 by simulated day 102, ahead of every published LLM agent's reported result and the human baseline.

How the DES actually models the vending machine

The comparison is only meaningful if the DES genuinely plays by the same rules the LLM agents faced: it never sees the environment's raw internal state, only a whitelisted observation snapshot, and every restocking, pricing, or cash decision goes through the same time-costed tool calls an LLM agent would have to make, rather than mutating the simulation directly.

That result isn't an argument that agents are pointless, it's the actual justification for Agentic Factory's shape: a bounded, well-specified operations problem doesn't obviously need an autonomous agent to solve it well, so the interesting question shifts from "can an agent do this" to "where specifically does agent-based coordination start winning over a rule-based or DES approach, and where does it not." Parts one and two below are built to answer that directly rather than assume an answer either way.

Part one: HarnessBench

Comparing agent frameworks fairly is harder than it sounds: each one has its own CLI, its own way of reporting what it did, and its own idea of success. HarnessBench standardises this by running every framework through a common adapter interface (OpenClaw, PicoClaw, NanoBot, NanoClaw, and a local demo mode for self-testing the benchmark itself, with over 100 defined tasks spanning file operations, terminal use, and other real-workspace actions) against fixtures mounted into a sandboxed workspace, so the same task, the same starting files, and the same grading criteria apply regardless of which framework ran it.

How a run actually happens

The CLI (harnessbench.cli) parses the command and task/model configuration and hands off to the runner, which is where the real work happens: it creates a per-task sandbox under a configurable work_root, copies that task's fixtures into sandbox/workspace (the only directory the agent actually reads and writes), renders the task's prompt, runs any task-specific hooks, then calls the adapter for whichever framework is under test. Once the adapter returns, the runner scores the result two ways: an oracle pass over the resulting workspace state for the outcome score, and, separately, a usage-proxy trace of the session fed to an LLM rubric for the process score. Both land in a single results JSON, keyed by model and task ID, alongside a token/usage summary when the framework's own session logs or the usage proxy can supply one.

How it's scored

The headline number is combined_score = outcome_effective × process_effective × security_score. process_effective is the arithmetic mean of three rubric-scored dimensions read off the usage-proxy trace, tool-use appropriateness, consistency, and robustness, with a separate binary security gate that can zero out the whole run regardless of how good the output looked. outcome_effective is normally just the oracle's programmatic outcome_score (did the workspace end up in the right state, checked directly rather than inferred); for the two tasks where correctness is genuinely fuzzy rather than binary (image recognition and image editing specifically), that oracle score is blended with an LLM quality judgement at a fixed 0.9 weighting in the oracle's favour, everywhere else the LLM quality signal isn't used for outcome scoring at all, deliberately, so a framework can't talk its way to a good result score on tasks where "did it work" has an actual, checkable answer.

Part two: agentic coordination vs. discrete-event simulation

Discrete-event simulation is the established way to model manufacturing throughput: define the process statistically (arrival rates, service times, resource constraints) and simulate the queue. It's mature and well-understood, but it assumes the process is stable and its statistics are known in advance, an assumption that breaks down around exactly the disruptions and edge cases a real factory floor deals with. The academic side of Agentic Factory sets that DES baseline up against agent-based coordination on the same underlying factory model, to see where each approach actually wins rather than assuming agentic coordination is strictly better because it's newer: DES for the well-behaved, statistically stable parts of the process, agent coordination for handling the disruptions DES has to model away or ignore.

Six coordination architectures are compared head-to-head against the DES baseline, not just one: a single agent working alone, a supervisor/worker split, a dual-loop design, a shared blackboard, an AI-informed DES, and an approval-gated variant. Every architecture runs against the same environment, the same fixed seed set, and the same tool interface, with operational, computational, and system-level metrics captured identically before a paired statistical comparison is run per scenario, per seed, and per architecture group.

The scenario suite itself is deliberately tiered rather than a single difficulty level: eighteen problems climbing from a deterministic single-order baseline, through stochastic timing, machine contention and routing, mid-run disruption (breakdowns, stock shortages, shift-change capacity dips, operator absence), priority and natural-language context, up to multi-agent and compounded-complexity scenarios, grouped further by how many production routes a floor actually runs.

Part three: the natural-language demonstrator

The third part is deliberately marketing-facing rather than a benchmark: describe a production design in natural language and watch a real agent carry it through the actual factory floor, live, rather than a static mockup of what the system could do if it existed. "Design My Order" is a standalone 3D configurator, pick a garment, describe a design (a prompt box example reads "a roaring lion badge in gold and navy"), hit "Make it", and the request goes to a real running agent to schedule and produce, with a direct link through to watch that exact order move through the live factory dashboard above.

The same free-text channel also lets a person mid-run redirect the agent, not just place new orders through it, "deprioritise ORD-014, it's not urgent" typed into the compare dashboard's instruction box has to be attributed to a real order, classified into an actual scheduling effect, and executed through the agent's normal tool surface with a human-readable log entry, not silently acknowledged and dropped.

Headline results

  • A from-scratch DES baseline, reading the same restricted observation an LLM agent would, outperformed all nine published Vending-Bench LLM agents and the human baseline on final net worth across 50 seeds, directly motivating where the rest of the project focuses agentic coordination.
  • A common adapter interface lets a new agent framework be added and benchmarked against the existing 100+ task suite without changing the scoring or task definitions themselves.
  • Process scoring from the usage-proxy trace gives a read on how an agent worked (tool use, consistency, robustness, security) independently of whether the final output happened to be correct, separating "got the right answer" from "got there safely and sensibly."
  • Outcome scoring is deliberately oracle-first: only two of the 100+ tasks let an LLM quality judgement influence the result score at all, and even then at a fixed, oracle-dominant weighting, so the benchmark can't be gamed by an agent that's good at sounding convincing.
  • Token and usage accounting is tracked per run, making cost/performance trade-offs between frameworks directly comparable rather than anecdotal.
  • Six coordination architectures, not one, are compared against the DES baseline across an eighteen-scenario tiered suite, so "agents beat DES" or vice versa is a scenario-and-architecture-specific finding, not a single headline claim.
  • The DES-vs-agent comparison runs live, not just as a one-off offline result: the same seeded factory floor is worked simultaneously by a real agent and a DES shadow, with throughput, cycle time, queue time, tardiness, and machine utilisation streamed to both sides of the dashboard as they happen, down to which individual orders are late or unfulfillable.
  • "Design My Order" closes the loop from natural language to physical schedule: an order typed into the configurator is a real instruction to the running agent, not a canned animation, and is traceable through to the same live factory view the DES comparison uses.
  • Mid-run natural-language steering (re-prioritising or holding an order by typing an instruction) is attributed, classified, and executed through the agent's normal tool surface with a logged reason, rather than being a free-text box that quietly does nothing.
