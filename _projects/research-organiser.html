A local web app for managing my own academic reading life: uploading PDFs, tracking what I've actually read, taking notes, building a citation graph, and keeping a research diary — all stored on my own machine rather than in someone else's cloud. This is a walkthrough of what it actually looks like to use it, screen by screen.

What it is

Under the hood it's a FastAPI backend with a SQLite database and a plain-JavaScript frontend (no build step) — you run it locally with python main.py and open localhost:8000. There's no separate account system or external server: every profile's library, diary, and reading queue live in one local research.db file, and uploaded PDFs sit in an uploads/ folder next to it. The one external dependency is optional — a free Groq API key, used to auto-extract metadata and generate summaries when you upload a paper.

Getting it running

Setup is three steps: get a free API key from console.groq.com (no card required), drop it into a .env file as GROQ_API_KEY=..., then start the server. On Windows that's .\start.ps1; on macOS/Linux, bash start.sh. Both scripts install dependencies, create the .env from the template if it doesn't exist yet, and check whether port 8000 is already taken before launching — or you can skip the script and just run pip install -r requirements.txt followed by python main.py directly. Either way, it comes up at http://localhost:8000.

Profiles

The app opens on a profile picker rather than a login screen (pictured above) — there's no password, since everything is local to your own machine. Profiles exist so you can keep separate libraries for separate projects, or so more than one person can use the same install without their reading queues getting mixed together. Every profile has its own library, diary, and queue, except for one shared “Bridging Papers” collection that's visible across all profiles — useful for papers that are relevant to more than one project.

The library

This is the main screen and the one you'll spend the most time on. Papers go in by drag-and-drop or the “Add papers” button, multiple at a time, and uploading doesn't block the UI — the AI metadata extraction (title, authors, year, journal, DOI, abstract, research fields, a short summary, and a first pass at cited references) runs in the background while you keep working, and each card shows a pending indicator until it's done.

Down the left, papers are organised by reading status — Unread, In Progress, Completed — and by colour-coded topics you define yourself, with a running count next to each. The main panel supports grid, list, and compact views, sorting by date added, rating, or publication year, and a search box that matches on title, author, DOI, or your own notes. Each paper gets a 1–5 star rating, a page-progress tracker, and a notes field that autosaves as you type.

The reference graph

The /graph page turns the library into an interactive 3D force-directed network (built on 3d-force-graph, so it's WebGL/Three.js under the hood, not a static plot). Nodes are colour-coded by reading status — unread, reading, read — plus two extra categories for papers the graph knows about but that aren't in your library yet: cited-but-not-uploaded references, and papers the AI has suggested you read next based on what's already there. Clicking a node opens an info panel with its summary and connections, and a direct link back to that paper in the library. There's also a separate Extraction tab: a table view of AI-extraction status per paper, with the per-paper reference list the graph edges are actually built from — useful for spotting a paper the extraction step choked on.

Analytics

A dashboard of what your library actually looks like: total papers, how many are currently being read, finished, or unread, completion percentage, and total pages read. Below that, a papers-added-per-month bar chart, a status-breakdown donut chart, a rating-distribution bar chart, and a ranked bar chart of your top research fields (drawn from the AI-extracted field tags), plus breakdowns of top authors and topics. It's a nice sanity check on reading habits — a fast way to notice that you have, say, fifteen unread nuclear physics papers piling up.

Diary and tasks

The /diary page is a dated research journal, separate from per-paper notes: entries can be searched by text, linked to specific papers, and exported as Markdown with YAML frontmatter (title, date, linked papers) if you want them somewhere else too. A second tab, Tasks, is a straightforward to-do list with priorities (low/medium/high/urgent), due dates, and a status of todo/in-progress/done, with overdue tasks highlighted so they don't quietly disappear.

Resources

A catch-all for material that isn't a paper: a Videos tab for saving YouTube videos with auto-fetched title and thumbnail (via YouTube's oEmbed metadata), tagged by topic and watchable inline; a Playlists tab for the same with an embedded player; and a Datasets tab for tracking datasets by source URL, description, and file upload, for when the thing you need to keep track of is data rather than a paper.

The rest: code, feed, and the research agent

Three more sections round out the app, though I don't have screenshots of these yet to show. /code is a place to save syntax-highlighted code snippets (Python, JS, R, MATLAB, C, Bash, Julia) and link them to the paper they came from. /feed is a small social layer — post research updates as a Read, Insight, Recommendation, or Note, optionally with a photo attached, and follow other profiles to see theirs. And /agent is a natural-language question box over your entire library: it reads paper summaries, abstracts, and metadata to answer grounded questions and cites the specific papers it drew on, with clickable links back into the library. Like the metadata extraction, it runs on Groq/Llama 3.3, so it needs the same API key already set up in .env.

Stack

FastAPI + SQLAlchemy + SQLite on the backend, PyMuPDF for PDF parsing, and a vanilla-JS frontend with no build step. The reference graph runs on 3d-force-graph (Three.js/WebGL); code highlighting is Prism.js.

A few practical notes

Everything stays local: uploads/ and research.db are gitignored if you keep the project in version control, and so is .env, so your papers, notes, and API key never end up committed anywhere. If a cited paper's title matches one already sitting in your library, the reference graph links them automatically rather than treating them as two separate things. And because AI analysis runs in the background rather than blocking the upload, it's entirely reasonable to drop in a stack of twenty PDFs at once and just let the pending indicators clear on their own while you keep working.
