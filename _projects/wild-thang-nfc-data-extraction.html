Wild Thang started as a simple problem: get staff to log which machine they're on and what job they're doing, without buying into a commercial time-and-attendance system. It grew into something more interesting once one particular machine — an HCR3 embroidery machine, nicknamed DARREN — needed its production data extracted automatically too, which meant teaching a Raspberry Pi to physically operate the machine's touchscreen on command.

The front end

Every machine gets the same NFC tag/QR code, pointing at one URL. Tap it, pick your machine from a dropdown, and choose one of three actions: Check In, Change Your Job, or Extract Data. Check In and Change Your Job ask for an employee ID and a job — the job list is pulled live from a shared Outlook calendar via Microsoft Graph when that's configured (each calendar event's subject becomes a job name), falling back to a plain text field otherwise, silently and without breaking anything for the person on the shop floor. Extract Data is gated behind a confirmation checkbox ("I confirm this machine is definitely not currently running") before it'll do anything, since triggering an export mid-job is exactly the failure mode worth designing out.

There's deliberately no login. Picking a name from a dropdown isn't authentication, and it doesn't need to be — this is a workshop-floor logging tool, not an access-control system. Every tap logs an event straight into a MongoDB nfc_log collection.

The extraction pipeline

This is the part that turned into a real hardware project. The HCR3 control box has no API, no network port, and no way to export data except by tapping through its own touchscreen menus and saving a CSV to a USB drive. So the Pi becomes that USB drive — and the mouse.

A Raspberry Pi 4, connected to the HCR3 over a single USB-C cable in USB gadget mode, presents itself as two devices at once: a USB HID mouse (absolute-position, so it can teleport the cursor to an exact touchscreen coordinate and click) and a USB mass-storage device backed by a disk image file living on the Pi's own microSD card. When "Extract Data" is pressed on the web page for machine 1, the Pi's Flask backend replays a pre-recorded tap sequence — wake the pointer with a right-click, open the menu, open REPORT, tap through all four report categories, save each one to the "USB drive," return home — then reads the exported CSV straight back out of its own disk image (briefly detaching the gadget, loop-mounting the image read-only, then reattaching) and uploads any new rows to MongoDB, deduplicated against a unique index on (machine_id, "No.") so a bug in the row-tracking can never double-insert a row.

Calibrating the tap sequence

The tap coordinates aren't guessed — they're measured against real photos of the HCR3's own 800×480 touchscreen, tapped through by hand while noting each screen's pixel position and load time, then encoded into a small CSV (taps.csv: x, y, button, wait_ms, note per row). A set of hardware-free preview scripts overlay the recorded tap sequence (or, for touch targets that need a real cursor path rather than a teleport-click, a recorded move-then-click session) on top of those same screen photos, so the whole sequence can be sanity-checked by eye before it's ever run against the real machine. A small local control panel (browser-based, or a Tkinter desktop equivalent) ties this together for bench testing: switch between tap-sequence and recorded-session input modes, preview either one, or kick off a real recording session on the Pi over SSH.

A second, separate script polls the same nfc_log collection this laptop watches for new "Extract Data" events on the HCR3 and pops up a full-screen preview automatically when one happens — visible feedback for a trigger that otherwise runs invisibly on a Pi sitting inside a workshop.

Getting the Pi talking to the machine

The USB gadget setup is the fiddly part: `config.txt` needs dtoverlay=dwc2,dr_mode=peripheral to put the Pi 4's USB-C port into peripheral (gadget) mode rather than host mode, which also means USB-C can no longer power the Pi — it needs a separate 5V supply. The gadget itself is a composite HID + mass-storage device, set up once via a systemd-managed install script and confirmed by checking /dev/hidg0 exists after boot. The Pi is reached over SSH by mDNS hostname rather than a fixed IP, since which network it's actually on (university Wi-Fi, direct Ethernet tethering, etc.) changes what IP it gets, and the mDNS name is the one thing that doesn't.

The backend itself — the Flask app serving the web page's API and triggering exports — runs on the Pi as a systemd service, exposed to the internet through a Cloudflare Tunnel rather than a port-forward, since the Pi has no public IP of its own.

Where the data actually goes: the Twin Thang dashboard

The extraction pipeline on its own just gets rows into MongoDB — it doesn't answer "how's the shop floor doing right now." That's a separate, sibling project: Twin Thang, a real-time 3D digital-twin dashboard (Vite + Three.js frontend, FastAPI backend) that reads the same wild_thang_real_and_synthetic collection this pipeline feeds and turns it into a walkable 3D view of the machines — DARREN among them — alongside a production Gantt chart, per-machine utilisation and thread-break stats, and an LLM-backed chat assistant for querying the data in plain English. It's downstream of everything described above, not part of the NFC/extraction system itself, but it's the reason the extraction pipeline exists in the first place: there'd be nothing for the dashboard to show without it.

Stack

Static HTML/CSS/vanilla JS front end; Flask backend on the Pi; MongoDB for event logging; Microsoft Graph (optional) for the Outlook job list; Cloudflare Tunnel for public exposure; systemd for service management; a Linux USB gadget (configfs-based HID + mass storage) as the actual mechanism for talking to the HCR3's touchscreen and reading back its export.
